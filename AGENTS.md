# AGENTS.md

## Project overview

`slurmtop` is one Python package with one console script of the same name: a [Textual](https://textual.textualize.io/) dashboard for a Slurm cluster in the style of `htop` (and of the unrelated [hunoutl/slurmtop](https://github.com/hunoutl/slurmtop)): partitions, the caller's account/QOS limits, a grid of estimated start times from `--test-only` probes, and the caller's jobs. One tab per cluster: the local one (if Slurm runs here), then each config entry with an `ssh` host, read over ssh. Only the local cluster is checked at startup; a remote one is first contacted when its tab is opened (`ClusterView.activate`), and only the visible tab refreshes. When output is not a terminal it prints the same panels once instead. It takes no options: the cluster is detected from `scontrol`, and the probe request is edited in the dashboard. It binds no keys: everything is a click (see **Mouse only** below). `Email: off` in the action bar turns on an hourly email of the report (see **Hourly email** below), which stops when the dashboard exits; `Config` edits the config in a form and applies it (see **Config reload** below). Textual's command palette is off (`ENABLE_COMMAND_PALETTE`). It works on any cluster: everything comes from Slurm, and the few site rules Slurm cannot report live in data profiles.

## Layout

- [pyproject.toml](pyproject.toml) — project metadata; console scripts live under `[project.scripts]`
- [src/slurmtop/cli.py](src/slurmtop/cli.py) — entry point (no options besides `--help`); lists the clusters (`find_clusters`), then runs the dashboard or, when output is not a terminal, the text report of the local cluster (remote ones only when Slurm is not available here)
- [src/slurmtop/hosts.py](src/slurmtop/hosts.py) — where commands run: `Local` (subprocess) or `Remote` (ssh). `run_batch` runs a refresh's commands in parallel, in one ssh session for a remote; `run_stream` reports probe results as they land, over a few ssh sessions
- [src/slurmtop/slurm.py](src/slurmtop/slurm.py) — the `scontrol`/`squeue`/`sacctmgr`/`sbatch`/`srun` command lines (`*_COMMAND`, `*_command`, `test_command`) and the pure parsers for their output
- `~/.config/slurmtop/config.toml` (`profiles.CONFIG_PATH`; under `$XDG_CONFIG_HOME` when set) — the only config (`profiles.load_config`; without it there are no profiles, no remote tabs and no email): `[mail]` (`profiles.load_mail`, whose address becomes `Settings.mail_user`), `[smtp]` (`profiles.load_smtp`, the hourly email's server and password) and `[clusters.*]`. The dashboard's config form (`C`, `tui.ConfigScreen`) writes it (`profiles.save_config`: `dump_config`'s TOML, mode 0600, atomically) after `profiles.check_config` applied the loaders' rules (`parse_mail`/`parse_smtp`/`build_profile`) to the form's values. It holds the SMTP password, so it lives outside any checkout: never commit, print or package a copy (a stray `config.toml` in the repository is still git-ignored)
- [src/slurmtop/profiles.py](src/slurmtop/profiles.py) — `Profile` (GPU count mode, ssh host) and `Smtp`, loading/validating the config file, and writing it (`dump_config`/`save_config`)
- [src/slurmtop/snapshot.py](src/slurmtop/snapshot.py) — `ClusterInfo.detect(host)`; `Collector(info, host)` builds a `Snapshot`: partition and hardware usage, account/QOS `Scope`s and their `Limit`s (QOS and association), and the caller's jobs; `Cluster` pairs a tab name, profile and host
- [src/slurmtop/probes.py](src/slurmtop/probes.py) — the estimates `Grid`: request sizes × walltimes, run concurrently with `--test-only`
- [src/slurmtop/views.py](src/slurmtop/views.py) — plain-text cells shared by both front ends
- [src/slurmtop/tui.py](src/slurmtop/tui.py) — the Textual app (`SlurmtopApp`: tabs, the action bar), one `ClusterView` per tab (its state, panels, workers and actions) and the probe-request dialog
- [src/slurmtop/report.py](src/slurmtop/report.py) — the text report printed when output is not a terminal; `print_cluster` prints one cluster's and returns its snapshot
- [src/slurmtop/mailer.py](src/slurmtop/mailer.py) — the hourly email: builds it (`digest`, `job_changes`, `compose`), sends it (`send`) and keeps the thread and last jobs in `~/.local/state/slurmtop/mail.json` (`send_report`); `SlurmtopApp` runs it on a thread worker from an hourly timer
- [tests/](tests/) — `unittest` suite; one module per source module, plus `fakes.py` (`FakeHost`, canned command output)

## Commands

```bash
uv sync                          # install/refresh the environment
uv run slurmtop                # dashboard for the cluster you are on
uv run slurmtop | less         # one-shot text report of this cluster
uv run python -m unittest discover -s tests -t tests   # run the tests
```

Note the `-t tests` on the test command: `tests/` has no `__init__.py`, so discovery fails without it. `test_report` and `test_tui` import fixtures from `test_snapshot`/`test_report`, which also relies on `-t tests`.

## Conventions and gotchas

- Python 3.12 only (`requires-python = "==3.12.*"`), managed with `uv`; build backend is `uv_build`. Textual is the only runtime dependency, and `cli.py` imports it only for the dashboard.
- Lint with `uvx ruff check src tests`.
- Nothing outside `hosts.py` starts a process; everything else receives a host and calls `run`/`run_batch`/`run_stream`. Commands never read the terminal (`stdin=DEVNULL`, `ssh -T -o BatchMode=yes`), or ssh would steal the dashboard's keystrokes. slurmtop never logs in for the user: a cluster that needs a password or MFA is reached through a control master the user opened with `ssh` in their own terminal (see **Remote clusters**). A tab that cannot connect, and the text report, show ssh's error with `hosts.connect_hint`; `Refresh` retries. `act` runs a command that acts (`sbatch`, `scancel`) and returns its status and combined output, so a rejection can be shown.
- Every duration a panel shows (time limits, wall caps, walltime columns, waits, job times) is Slurm's `D-HH:MM:SS`, via `slurm.format_duration` (minutes) or `slurm.normalize_time` (squeue strings). `∞` marks no limit.

### Supporting a new cluster

Usually nothing is needed: the cluster name comes from `scontrol show config`, and partitions, GPU types, time tiers, accounts and limits are all read from Slurm. Add a profile only for rules Slurm does not report, as a `[clusters.<ClusterName>]` table in the user's config (a row in the form). The README's **Other clusters** section records the known clusters' rules; add a new cluster's there too:

- `gpu_counts` — `pow2` (default), `all`, or `whole_node` for sites that reject partial GPU nodes (`tamia`). `whole_node` also makes each GPU request take its whole node (`Request.whole_node`: `--exclusive --mem=0`), since holding every GPU with only the request's few CPUs and memory would waste the node.

Do not add per-cluster code paths; if a cluster needs logic rather than data, generalize it in `snapshot`/`probes` behind a profile setting.

Slurm reports the same facts differently per site; the generic code already handles these:

- **Rejection reasons.** Submit filters print banners or notes on every submission (RCL's storage-policy banner, Fir's and Tamia's note on G vs 1000M memory units), rejections included. `probes.clean_message` strips colour codes, `sbatch:`/`srun:` prefixes and `-----`/`=====` rules, and leaves out every line an accepted reply printed too (`Grid.banner`, learned by `learn_banner`; a rejection that landed first is cleaned again). The view and the report share one banner set across a cluster's grids. If no probe is ever accepted, banners stay in the reasons.

- **Reserved cores.** `slurm.parse_nodes` records `cpu_tot` (`CPUTot`) and `cpu_efctv` (`CPUEfctv`, falling back to `CPUTot`). Usage and hardware groups always use `cpu_efctv`, so `CoreSpecCount` cores never show as free.
- **GPU rollups.** `CfgTRES` may list an untyped `gres/gpu=N` alongside per-model entries summing to the same `N`. `parse_tres_gpus` returns both; `Collector` calls `normalize_gpu_rollups` on every node so GPUs are not counted twice.
- **Unavailable nodes.** `slurm.node_available` checks every state word (`IDLE+DRAIN`, `DOWN+NOT_RESPONDING`...); unallocated capacity on such nodes is "unavailable", not free.
- **Partition routing.** Probes never pass `--partition` unless the user adds it; Alliance clusters and `rcl` route jobs by duration or GPU request. Default walltimes are the distinct `MaxTime`s of usable partitions (`plan_walltimes`), which is where routing changes.
- **Probe sizes.** Each GPU type is probed up to the tightest GPU cap in the scope's limits (`max_gpu_counts`: per job, user, account or node, on the model or all GPUs), never above one node's capacity. Walltimes above the scope's wall cap are skipped, not probed.
- **Whole nodes.** `Settings.whole_node` swaps `-c`/`--mem` for `--exclusive --mem=0` (`resource_directives`) on every row and makes `build_grid` probe each GPU type at full node capacity, like the `whole_node` profile mode. The profile mode does the swap for GPU rows only (`Request.whole_node`; `Grid.gpus_by_node` notes it on the panel and in the report), leaving the CPU-only row on `-c`/`--mem`. `Settings.describe()` is the one-line request shown on the estimates panel and in the report.
- **Submitting.** `Result.run` is the submit command as arguments (`slurm.run_command`, the same one `format_run_command` shows), so Submit runs exactly what is displayed and copied. `ConfirmScreen` always asks first, with Cancel focused, before Submit (`sbatch`) or Release (`scancel`); rejected cells and `srun` commands (interactive, so they need a terminal of their own) are refused. Like everything else, submitting, releasing, copying, switching clusters, account/QOS, sbatch/srun and Partitions/Nodes by hardware are clicks (the tabs switch clusters): the `Submit` label in Details carries `@click` meta for `app.submit` (sbatch only), `Release` in a job's details for `app.release_job` with the job id, and every command's `Copy` link (`copy_link`, a `CommandLine` suffix) for `app.copy_command` with the command itself, the command in the Start estimates subtitle for `app.toggle_command`, the Partitions and Nodes by hardware titles for `app.toggle_nodes`, and the estimates' title (the probed account/QOS, clickable only when there is another) for `app.next_scope`; the app actions forward to the visible tab, since a click's default namespace is the widget that drew the text.
- **Mouse only.** slurmtop defines no key bindings anywhere: no `BINDINGS`, no Footer (`SlurmtopApp.actions()` draws an action bar docked at the bottom instead), no Escape in dialogs (each has a Cancel button) and no Enter-to-submit in form fields. Each action bar label carries `@click` meta for an app action: `refresh`, `probe` and `edit_request` forward to the visible tab, and `set_mail(on)` takes the state to switch to, so the label always reads `Email: on` (green) or `Email: off`; `update_actions` redraws it when the email starts or stops. A click on the highlighted Accounts & QOS row probes with it: DataTable posts `RowSelected` only for a click on the row the cursor is already on, so the first click highlights. Textual's own widget behaviour (typing, Tab focus, arrows in a table, `ctrl+q`) is left alone. Tests click with the pilot: `click_action` (action bar), `click_cell`/`click_row` (tables, placed from the columns' render widths) and `click_detail` (Details).
- **Config reload.** `Config` in the action bar (`action_edit_config`) opens `ConfigScreen` on `load_config()` (empty when the user has no file; a file that broke since startup is noted in the form and replaced on save). The form is compact one-line fields so it fits a 44-row terminal with a few clusters and scrolls beyond; GPU counts is a `Select` of `profiles.GPU_COUNT_MODES` (no blank, defaulting to `Profile.gpu_counts`, which `ClusterRow.values()` leaves out of the file), so it cannot hold a value the loader rejects; `ClusterRow.values()` and `ConfigScreen.values()` turn it back into `load_config`'s dict, leaving out blank tables and fields (a blank `[mail]` address drops the table; a port that is not digits is kept as text so `check_config` reports it). Saving dismisses with True and `reload_config` loads every table first (a `ValueError` is reported and nothing changes) and applies them without a restart: a changed `[mail]` table reaches every view's `Settings` and re-probes (unchanged, it leaves an address edited per view with `Edit request` alone; the app's `settings`, which new tabs start from, records the config's values); a changed `[smtp]` replaces the hourly email's server while it is on, and a removed one stops it; profiles change in place (`ClusterView.set_profile`, re-probing when the GPU counts changed); clusters with an `ssh` host gain or lose tabs (`add_cluster`/`remove_view`; a changed host counts as a new cluster; the local tab and the last tab are never removed). Pane ids are `cluster-<n>` from a counter that is never reused, and `SlurmtopApp.view` finds the visible view by its pane id, not by index, so `views` stays a plain list that `send_mail` iterates.
- **Email.** `Settings.mail_directives()` adds `--mail-type`/`--mail-user` to every run command (`Grid.run_directives`) but not to probes (`Grid.probe_directives`), which carry only what the estimate depends on: the request (`request_directives`) and extra options. The request dialog edits the address per view; it rebuilds `Settings` with `dataclasses.replace`, so fields it does not show survive.
- **Hourly email.** `Email: off` reads `[smtp]` when clicked, sends at once and then from an hourly `set_interval`; the timer dies with the app, so nothing runs after exit (`crontab` is not allowed for users on Killarney's login nodes anyway). Each email covers the local cluster and remote tabs that have data (opened at least once), each with its view's `Settings`; never-opened tabs are not contacted. `report` prints to an `out` stream so the email collects the text without redirecting `sys.stdout`, which Textual owns while it runs. One conversation needs both the same subject and `In-Reply-To`/`References` pointing at a message the client has, so the first email's `Message-ID` is stored per recipient and every later email refers to it (Message-IDs themselves must stay unique: Gmail drops duplicates). The state file is written only after a successful send, so a failed email's changes appear in the next one. The body is also sent as HTML `<pre>`, since Gmail's web client shows plain text in a proportional font and the tables would not line up. `send` refuses to log in without STARTTLS or SSL. `Smtp.password` is kept out of `repr`.
- **Run commands.** Each `Result` keeps the probe as it ran (`probe`, from `slurm.format_test_command`) and its raw `output`, both shown in the estimate's details, apart from the command to submit (`command`, from `format_run_command`, which the `Copy` label copies). Both use `slurm.SBATCH_WRAP` (`--wrap="sleep infinity"`) instead of a batch script, so the submit command is the probed request without `--test-only`, plus email and `slurm.SBATCH_OUTPUT` (`--output=/dev/null`, so the placeholder leaves no `slurm-<jobid>.out` where sbatch ran; probes create no file, so they leave it out); `srun` probes name the login shell (`Grid.shell`, the remote user's shell on a remote cluster) and `srun` commands run it with `--pty <shell>`. Naming a program matters: Tamia's submit filter only routes an `srun` that names one ("No partition specified" otherwise), and on Killarney the estimates are the same either way. Keep them in step when changing either.
- **Default account/QOS.** `Scope.directives()` leaves out `--account`/`--qos` when Slurm would pick them anyway: the account when it is the caller's only one, and the account's default QOS (`default_qos` mirrors slurmctld: `DefaultQOS`, else the only QOS, else `normal`). With several accounts `--account` is always passed: Fir's submit filter rejects GPU jobs that leave it to the default ("You are associated with multiple _gpu allocations"). `Scope.user_default` still marks the `DefAssoc=Yes` account, which picks the initially probed pair.
- **Preemptible partitions** (`PreemptMode` other than `OFF`, such as Fir's 122-day `cpupreempt`) are not routing tiers and do not add walltime columns.
- **GPU names.** `slurm.gpu_display_names` shortens MIG and vendor names for display (`nvidia_h100_80gb_hbm3_1g.10gb` → `h100 1g.10gb`), keeping full names where short ones would collide; `--gres` always uses the real type.

### Reading account limits

`sacctmgr` works on Killarney and supplies the caller's account/QOS assignments (with `DefaultQOS`).
On some sites, `sacctmgr` and `sacct` fail from a login shell when `slurmdbd` listens on the controller rather than locally ("Connection refused" to `localhost:6819`). That is **not** evidence that accounting is disabled — check `AccountingStorageEnforce` in `slurm.conf`, which is world-readable. Use `scontrol show assoc_mgr flags=assoc,qos` instead: it reads slurmctld's in-memory cache and works unprivileged. Its `users=` filter does not filter, but `accounts=` and `qos=` do: the whole cache is fetched only to discover accounts when `sacctmgr` fails, and later refreshes ask for the caller's accounts and QOS alone.

When `sacctmgr` fails, `discover_scopes` pairs every account from `parse_user_accounts` with every cached QOS and drops each pair whose minimal CPU-only `sbatch --test-only` is rejected as an invalid account or QOS (`accepted_pairs`, all pairs in one stream). A QOS a partition refuses is kept: that reply is not "Invalid".

These quirks of the `assoc_mgr` output shape the parsers in [slurm.py](src/slurmtop/slurm.py) and `scope_limits` in [snapshot.py](src/slurmtop/snapshot.py):

- Association records carry **no** `QOS=` field. QOS `Account Limits` blocks track account usage, not permissions: an allowed QOS may omit the caller's account entirely. Cache membership neither identifies the default QOS nor establishes which QOSs the user may use.
- `MaxJobsPA` / `MaxSubmitJobsPA` / `MaxTRESPA` under `Account Limits`, and `MaxWallPJ` (minutes) / `MaxTRESPN` at QOS scope. Account usage covers all users within that QOS; it is separate from the caller's per-user usage. A missing account entry can borrow QOS caps from another account, but never its usage.
- `MaxJobsPU` / `MaxSubmitJobsPU` are only rendered inside per-user entries under `User Limits`, and a user with no tracked jobs has no entry at all. Since a QOS applies one value to every user, `qos_user_limits` falls back to another user's entry for the limits — take only the limit, never the parenthesised usage, which is that other user's. If no entry supplies a limit, show `?`. With no entry and no running jobs in the QOS, the caller's usage is 0. Job usage comes from `squeue`, scoped to the user and each QOS across all accounts.
- Association `Max*` limits are inherited down to the caller's own association, so `scope_limits` reads `Max*` there and only `Grp*` totals from the account and its parents (`association_chain`, stopping at `root`).

### Remote clusters

Measured on Alliance login nodes: starting an ssh session costs ~0.15 s on Fir but ~2.5 s on Tamia (shell start-up), while each Slurm command inside a session is fast. Hence one session per refresh (`run_batch`), probes streamed over `PROBE_WORKERS` sessions (`run_stream`), and `ClusterInfo.detect` doing everything in one session with `login_path=True`: non-login ssh sessions on Fir lack Slurm on `PATH`, so detection reads the login shell's PATH (`bash -lc`) and later scripts export it. The unfiltered `assoc_mgr` cache on Fir is 66 MB (8 s); `Collector` filters it to the caller's accounts and QOS (`assoc_mgr_command`), fetching parent accounts' associations separately (`with_parent_associations`, inserted before `QOS Records`). Only the visible tab refreshes on the timer; hidden tabs are not contacted at all, so a control master can expire while its tab is hidden; reopening it then reconnects where keys need no prompt, and otherwise shows the error until the user logs in again.

When the user's `~/.ssh/config` already multiplexes (`ControlMaster`/`ControlPath`, read with `ssh -G`), `Remote` reuses that master, which is how a cluster that needs a password or MFA is reached: the user logs in with `ssh` in another terminal. Otherwise it adds its own socket in `$TMPDIR/slurmtop-<uid>/` with `ControlPersist=10m`, which only a prompt-free (key) login can open.

### Testing

The suite is pure `unittest` and needs no Slurm or ssh. Only `hosts` starts processes, so `test_hosts` patches `hosts.subprocess`, and everything else runs against `fakes.FakeHost`, which answers commands by prefix from canned text and probes through a `probe(args)` function. Note that `str.splitlines()` splits on `\x1e` (the record separator `hosts` uses), unlike a pipe; fake pipes use `io.StringIO`. Parsers are pure functions exercised with captured output. `test_tui` drives the app headlessly with Textual's `run_test` pilot (`IsolatedAsyncioTestCase`), with a local and a remote fake cluster. `test_mailer` patches `mailer.smtplib` (or `mailer.send`) and `report.print_cluster`, so it sends no mail and runs no probes, and writes state to a temporary file; `test_tui`'s mail tests patch `profiles.load_smtp` and `mailer.send_report`; its config tests point `profiles.CONFIG_PATH` at a temporary file, fill the form's `Input`s directly, click its buttons with the pilot and replace `hosts.Remote` with `FakeHost`, so a cluster added in the form is never contacted for real. `test_profiles` points `CONFIG_PATH` at a missing file, so it never reads your own config, and saves one in a temporary directory.

End-to-end behaviour against a real cluster still needs a machine where `scontrol` works, and the probes additionally need `sbatch` or `srun`. Both use `--test-only` and never start a job, so running `slurmtop` is safe on a shared login node; only a confirmed Submit or Release (`ConfirmScreen`) starts or cancels one. Never confirm either from a test script on the real cluster. To check the dashboard's layout from a script, run it in a private tmux server (`tmux -L <name> new-session -d -x 150 -y 44 ...` then `capture-pane -p`) so the user's own tmux clients cannot resize it.
